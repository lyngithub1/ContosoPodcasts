Azure Scientific Podcast Studio

A self-service research-to-podcast factory for scientific & healthcare teams — it turns a topic into a cited evidence set, an evidence-grounded script, medically-accurate English & German narration, and a human-gated publication, all on Azure.

Medical & scientific media Evidence-grounded Human-gated publication Azure-native · managed identity WCAG 2.2 AA

01 Overview

The studio acquires research material, builds a cited evidence set, drafts a podcast script, supports staged human review, converts approved text into high-quality speech, lets non-technical reviewers fine-tune pronunciation and delivery visually, stores approved media privately in Azure, and distributes it to selected recipients only after explicit final approval. The repo is a runnable reference implementation of the build specification in spec/.

🌟 Mission

Turn a research topic into a traceable, cited podcast — natural EN/DE narration with trustworthy medical pronunciation, and nothing published without human approval.

🏗️ Approach

A fixed priority order drives every scope decision: speech quality & pronunciation → factual grounding → reviewer control → security → usability → speed → cost.

🛡️ Non-negotiables

Managed identity + Entra ID (no secrets in source), never auto-publish, immutable published artifacts, synthetic-media disclosure, and a complete audit trail.

▶ How to Use the Studio

A plain-language walkthrough for first-time users. You don’t need a cloud account or any setup knowledge — follow the steps in order and you’ll take a research topic all the way to a finished, approved podcast.

1. Open the studio (about a minute)

STEP 1

📦 Install once

With Node.js 20+ installed, open a terminal in the project folder and run npm install. You only do this the first time.

STEP 2

▶️ Start it

Run npm run dev. Leave that terminal window open — it keeps the studio running.

STEP 3

🌐 Open in a browser

Go to http://localhost:5173. That’s the studio. Everything stays on your machine — nothing is sent anywhere.

Just want to look around? The studio opens with a sample project already loaded (a German HIV research episode), so you can explore every screen without creating anything first.

2. Choose who you are

Different jobs in the studio are done by different roles. Use the role selector in the top bar to switch between them — the buttons and screens change to match what that role is allowed to do. For a full walkthrough, start as Creator, then switch to each reviewer role when it’s their turn.

3. Make your first podcast, step by step

STEP 1 · CREATOR

📡 Start a project & add research

Create a new project and give it a topic. Add your research by pasting article links, DOIs/PMIDs, or uploading documents. The studio gathers the material into one place.

STEP 2 · CREATOR

🔬 Accept the good evidence

Review each source and accept the ones you trust (or reject the rest). You need at least one accepted source before you can move on — this keeps the podcast grounded in real evidence.

STEP 3 · CREATOR

📝 Generate the script

Ask the studio to draft the script. It only uses your accepted evidence, adds an “this is AI-generated” disclosure at the top, and links each claim back to its source. Edit the wording as you like.

STEP 4 · CREATOR

🎤 Shape how it sounds

Select any word or sentence and open the “How should this sound?” panel to fix pronunciation, speed, emphasis, or pauses — in plain language. Preview just that part to hear the change instantly, then create the audio preview.

STEP 5 · REVIEWERS

⚖️ Send it for review

Switch roles (or hand off) to the Scientific, Medical/Legal, and Audio reviewers. Each checks their area and either approves or rejects with a reason. Rejections send it back for a quick fix — nothing is lost.

STEP 6 · PUBLISHER

📣 Publish it

As Publisher, confirm the recipient list and press publish. This is the only way anything goes out, and it happens only after every check has passed.

4. Good things to know

✋ Nothing publishes on its own

The app never sends a podcast automatically. A person with the Publisher role has to approve and publish it — on purpose.

🔍 Pronunciation is double-checked

The studio listens back to the audio and flags any medical term it heard wrong. If something important is off, approval is blocked until a reviewer signs off.

♻️ Everything is tracked

Open the Audit Trail screen to see every action — who did what, when, and why. Great for checking your work or showing the process.

If a button is greyed out, it usually means a required step isn’t finished yet (for example, you can’t make audio until the script is approved, and you can’t publish until the audio passes review). Finish the earlier step and the button turns on.

07 Roles & Workflow

Role-based access via Microsoft Entra ID groups and application roles. One user may hold multiple roles; least privilege is enforced server-side (not only in the SPA). Every approval records user, role, timestamp, content hash, comments, and the approved version.

RoleCan do
CreatorStarts projects, selects sources, generates scripts, requests review, creates audio previews.
Scientific ReviewerValidates factual accuracy, citations, terminology, and scientific balance.
Medical/Legal ReviewerReviews disclosures, approved language, safety language, and publication readiness.
Audio ReviewerReviews pronunciation, voices, pacing, prosody, loudness, and mastering.
PublisherApproves recipient lists and explicitly publishes an approved version. gates external recipients
AdministratorManages source allowlists, vocabularies, voice/model availability, retention, templates, channels.
Auditor / Read-onlyInspects evidence, versions, decisions, and publication history — cannot alter content.

Gating rules

🔑 Evidence gate

Research can't finalize without at least one accepted source. Every material scientific claim must map to one or more accepted sources.

🔑 Script gate

Script generation never implies approval. Audio generation stays disabled until a script version is approved.

🔑 Publication gate

Publication is disabled until audio approval, disclosure checks, recipient validation, and distribution review all pass.

🔑 Rejection is first-class

A rejection always requires a reason and creates a new task for the appropriate stage — nothing is silently reverted.

08 Speech & Pronunciation

The highest-priority feature. Non-technical reviewers select a word, phrase, sentence, or speaker turn and open a plain-language “How should this sound?” panel — the UI generates standards-compliant SSML behind the scenes and previews only the selected region for fast iteration.

🎧 Friendly controls

Pronunciation (“sounds like,” phonetic, IPA expert mode), speed, emphasis, pause before/after, pitch, volume, tone/style, language treatment (DE/EN/auto), and “speak as” (acronym, cardinal, ordinal, date, dosage, unit, trial ID, DOI, URL).

📚 Pronunciation library

A versioned organization glossary — canonical form, locale, spoken alias, IPA/phonemes, optional audio reference, therapeutic tag, approval state, and review history. Uses PLS/custom lexicon where the voice supports it, else word-level SSML.

🔍 Closed-loop QA

Every preview is re-transcribed with STT and compared against expected medical terms, numbers, drug names, trial IDs, and units. Critical-term mismatches block until reviewed; a reviewer may override with a required reason.

🎵 Voice / model comparison

Curated voice cards by locale and use case, A/B/C rendering of a short segment, blind comparison, and saved voice pairs per template / therapeutic area. Provider-adapter design keeps the catalog configuration-driven.

Provider-neutral annotation → SSML

User intent is stored as a provider-neutral annotation model, not raw SSML in editor content. At synthesis time it is validated against the voice capability profile, lexicon-resolved, and normalized with documented fallbacks — then frozen as an immutable synthesis artifact.

{
  "range": { "segmentId": "seg-42", "start": 12, "end": 27 },
  "pronunciation": { "locale": "de-DE", "ipa": "..." },
  "rate": "slow",
  "emphasis": "moderate",
  "pauseAfterMs": 350,
  "languageMode": "en-US"
}
Demo blocker to watch: in the seeded HIV episode, the term Tenofovir-Alafenamid trips a blocking pronunciation-QA mismatch — approval is gated until a reviewer records an override, exactly as the spec requires.

09 Security & Compliance

The design follows the spec's non-negotiables. The IaC grants least-privilege data-plane RBAC to a single user-assigned identity, and disables local/key auth on Storage, Cosmos, Speech, Search, and Service Bus.

🔐 Managed identity, no secrets

No credentials in source, client bundles, or config. Least-privilege RBAC data-plane roles; local/key auth disabled on data services; rare secrets go to Key Vault.

✋ Human-gated publication

Nothing publishes automatically; Publish requires an explicit confirmation summary and is idempotent + receipted. External recipients require the Publisher role; addresses are never exposed cross-recipient.

📄 Immutable + disclosed

Published artifacts are immutable — corrections create a new version. Synthetic-media disclosure is embedded in every publication; pronunciation entries are review candidates, never authoritative.

♿️ Untrusted content defense

Acquired web/document content is treated as untrusted: SSRF-safe URL validation, upload MIME/size/structure checks, quarantine-before-validate, and indirect prompt-injection defenses.

♻️ Complete audit trail

Access, state transitions, content changes, review decisions, model/voice choices, and publication events are all logged — with tokens, secrets, and unnecessary PII redacted from telemetry.

♿ Accessibility (WCAG 2.2 AA)

Keyboard-first, visible focus, skip link, status by icon + text (never color alone), accessible sliders + waveform alternatives, captions/transcripts, reduced-motion support.

Compliance honesty: using Azure does not make the app HIPAA, GxP, MLR, or otherwise compliant. The studio provides the technical controls and evidence the deploying organization needs for its own validation and governance — the claim is never made on Azure's behalf.

11 FAQ

What is real vs. simulated in this reference?
The domain model + workflow state machine and the SSML projection engine are real and unit-tested; the React SPA is runnable end-to-end. The backend APIs, AI/research, and speech synthesis are simulated in-browser using data seeded from real sample content, and the Bicep compiles and provisions the target topology. See KNOWN_LIMITATIONS.md for the honest, per-capability inventory.
Why doesn’t it publish automatically?
Human-gated publication is a spec non-negotiable. Publish requires an explicit confirmation summary, is idempotent, and generates a per-recipient receipt. External recipients require the Publisher role, and one recipient’s address is never exposed to another.
How does pronunciation stay medically accurate?
A closed loop: each preview is re-transcribed with speech-to-text and compared against expected medical terms, numbers, drug names, trial IDs, and units. Critical-term mismatches block approval until reviewed; a reviewer may override with a required reason. A curated “golden pronunciation set” regression-tests voice/model/lexicon changes.
Why are Cosmos and the compute tier in a different region?
The demo subscription has no Cosmos region access in West Europe or North Europe, and West Europe was hitting AKS capacity limits for Container Apps. New cosmosLocation and computeLocation Bicep parameters route Cosmos, Container Apps, and APIM to France Central; the rest of the resources remain in West Europe.
Is it HIPAA / GxP / MLR compliant?
No — using Azure does not make it compliant. The studio provides the technical controls and evidence (managed identity, RBAC, audit trail, disclosure, retention hooks) that the deploying organization needs for its own validation and governance process.
Can I run it right now?
Yes. With Node.js ≥ 20: npm install then npm run dev, and open http://localhost:5173. No cloud resources are needed and no network calls leave the browser — safe to demo offline.
